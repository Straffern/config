# Den flatness research

## Executive decision

Keep the current feature-first, mostly flat aspect layout. Do not flatten namespaces or introduce a new hierarchy rule. Flatten only a wrapper whose deletion leaves the same module interface, dependency DAG, scope behavior, and readable ownership seam; retain nesting when it communicates a real namespace, reusable module boundary, or scope/topology edge. This is a recommendation about this repository, not a new Den policy or quirk.

## Scope and method

I read the complete pinned Den documentation corpus: 16 explanation pages, 14 guides, 10 reference pages, and 12 tutorials (52 documents), then compared the findings with all 13 template families and 383 authored template files at revision [`e8e8de1e32646456cfc613f152175a7a548508ec`](https://github.com/denful/den/tree/e8e8de1e32646456cfc613f152175a7a548508ec). The template inventory is: bogus 6, CI 242, default 10, diagram-demo 26, example 21, flake-parts-modules 13, fleet-demo 23, microvm 9, minimal 5, noflake 6, nvf-standalone 6, scoped-import-tree 6, and terranix-demo 10. These counts describe the inspected corpus, not an architectural endorsement of every page, template, or file. The 242 CI files are a regression/test corpus, not recommended demos; the other families are examples or fixtures with different teaching purposes. ## What “flatness” means

- **Filesystem flatness:** concern files are siblings in a directory rather than nested directories. This is a navigation/locality property, not Den semantics.
- **Namespace flatness:** aspects are direct named keys (for example `igloo` or `tux`) rather than members below a namespace such as `eg.vm.gui`. Namespaces are real composition and lookup boundaries; they are not merely filesystem folders. [Aspects and namespaces](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/reference/aspects.mdx#L59-L104) [Namespaces guide](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/guides/namespaces.mdx#L12-L83)
- **DAG flatness:** an aspect can be a top-level node while `includes` still creates a directed acyclic dependency graph. “Flat” does not mean dependency-free or disconnected; providers, includes, excludes, and policies preserve graph edges. [Core principles](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/core-principles.mdx#L149-L228) [Aspect reference](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/reference/aspects.mdx#L106-L150)
- **Class-module flatness:** one aspect owns class outputs such as `nixos` and `homeManager`, and a class module receives the entity/module arguments it needs. This is distinct from namespace depth. Den explicitly supports flat class injection; context-dependent behavior may instead use an outer parametric aspect. [Class modules](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/class-modules.mdx#L25-L148) [Parametric aspects](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/parametric.mdx#L49-L130)

## Angle brackets: what they do and do not do

Angle brackets are optional `__findFile` path syntax: they shorten a lexical file lookup when the module argument and lexical `__findFile` arguments are available, with ordered resolution and a direct nested-key form preferred over the deprecated `provides` fallback. They change lookup spelling and interface cost, not aspect topology, namespace depth, class-module injection, scope, DAG edges, or policy semantics. A bracket reference therefore is not evidence that an aspect should be flattened (or nested). [Angle-brackets guide](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/guides/angle-brackets.mdx#L12-L83) [Library reference](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/reference/lib.mdx#L20-L70)

## Evidence: normative guidance, examples, and semantics

**Normative guidance.** Den recommends feature-first organization: a named aspect is the primary unit, with class-owned configuration; split modules by concern rather than building a monolith. `includes` expresses composition, while cross-entity delivery should use the supported pipeline/policy mechanisms. When context controls an entire aspect, outer parametric dispatch is the deeper seam; when only one class module needs entity data, flat injection is appropriate. [Core principles](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/core-principles.mdx#L149-L228) [From zero to Den](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/guides/from-zero-to-den.mdx#L65-L183) [Configure aspects](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/guides/configure-aspects.mdx#L18-L269) [Parametric guidance](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/parametric.mdx#L49-L130)

**Example patterns.** Tutorials mostly show flat, top-level host/user feature aspects; minimal explicitly has `igloo` and `tux` without namespaces, while example intentionally demonstrates `eg.vm.gui`/`eg.vm.tui` nested namespace aspects and angle-bracket references. Other tutorials demonstrate flat server/guest aspects, providers, fleet scopes, and parametric host-qualified aspects. These are patterns selected for teaching a feature, not a universal rule. [Minimal](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/tutorials/minimal.mdx#L51-L102) [Example](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/tutorials/example.mdx#L45-L150) [Tutorial overview](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/tutorials/overview.mdx#L20-L82)

**Source semantics.** Direct class keys and nested aspect keys are both supported; `includes`/`excludes` control dependency and suppression; `provides` creates provider namespaces; static functions emit once while context-argument functions are parametric. Diagram flattening is a view transformation, not a semantic requirement. [Aspect reference](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/reference/aspects.mdx#L59-L150) [Diagram reference](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/reference/diag.mdx#L35-L104)

## Comparison with this dotfiles repository

`modules/aspects/` already follows the evidence-backed feature-first shape: concern-owned aspects (`styles`, `desktop`, `cli`, `services`, `network`, `storage`, `tooling`, and similar) are separated from entity declarations, while profiles act as include graphs. Class behavior is kept inside an aspect’s native NixOS/Home Manager outputs, rather than creating class-named aspect layers. Host/user delivery uses Den’s existing providers/batteries and explicit routing. This matches the documented module/interface seam and avoids needless wrapper depth. [Core principles](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/core-principles.mdx#L149-L228) [Class modules](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/class-modules.mdx#L25-L148)
One important local routing seam is active rather than hypothetical: `modules/entities/hosts/sonic/default.nix:74` defines `den.aspects.sonic.provides.alex`, whose `includes` at lines 75–87 routes user-specific aspects and whose `homeManager` module begins at line 89. That cross-entity provider boundary is a reason to retain the nesting; flattening it would erase semantic delivery, not just a directory level.

The repository’s filesystem is not namespace-flat: concern directories and entity-owned private fragments provide locality and ownership. That is not a Den violation. Its aspect DAG is intentionally non-flat through profiles, batteries, includes, and providers, while its class modules are largely flat forms. The meaningful design seam is the aspect interface and routing edge, not the number of directory levels. [Aspects](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/aspects.mdx#L35-L122) [Batteries](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/reference/batteries.mdx#L20-L100)

## Deletion test and candidates

Apply this deletion test to every proposed wrapper: if deleting the directory/namespace/module preserves the public module interface, include/provider/policy edges, scope locality, diagnostics, and the owner’s ability to evolve independently, delete it; otherwise retain it. The test is about leverage and seam quality, not aesthetic depth.

**Retain:** feature-owned aspect boundaries; profiles that intentionally compose a coherent feature set; namespaces used for reusable or scoped sub-aspects; entity-private fragments; and any wrapper that carries a real policy, provider, class, or scope edge. These boundaries preserve locality and make the interface legible. [Policies](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/policies.mdx#L35-L150) [Scope partitioning](https://github.com/denful/den/blob/e8e8de1e32646456cfc613f152175a7a548508ec/docs/src/content/docs/explanation/scope-partitioning.mdx#L20-L120)

**Applied flattening:** Sonic now selects `den.aspects.apps.discord` and `den.aspects.apps.shotwell` directly; the one-edge `profiles.social` and `profiles.photos` aliases were deleted. The unused `profiles.video` and `profiles.gamedev` include graphs were also deleted as dead code. `modules/aspects/profiles/gaming.nix:2-4` remains: although mechanically thin, it is the named generic gaming seam consumed by the compositor-specific Niri integration. Do not flatten merely because a path contains brackets, `provides`, a class name, or more than one directory level.
`modules/aspects/profiles/desktop.nix:2-22` and `modules/aspects/profiles/development.nix:2-37` fail that deletion test as mere wrappers: they are deep composition modules with many deliberate includes. Deleting either would force each host/user caller to learn and reproduce the selection of its component aspects, moving architecture knowledge to callers and weakening the profile seam. Retain them as coherent selection modules.

## Recommendation

Keep the current layout and make no framework-level change. Treat feature aspects as the stable module interface; use profiles/includes for deliberate DAG composition; use namespaces only where they buy reusable scope or discovery; choose flat class injection versus outer parametric dispatch from the context seam; and use angle brackets only when their lookup convenience outweighs their enabling/interface cost. Keep CI’s 242 files as regression coverage, but do not present CI fixtures as recommended demos. Any future flattening should be a local deletion-test refactor with unchanged Den policy, quirk, and routing semantics.
